# Design

**The look is editorial and it is contained.** — Patrick, 15 October 2026, on the design
pass: the serif, the sans and the one green stay; what had to go is the sprawl. *"Everything
seems to be a bit sprawling across the page at the moment."*

This file is the **patterns**. The **values** are in
[`web/app/assets/css/tokens.css`](../web/app/assets/css/tokens.css), which is documented at
length and is the only place a colour, a radius, a lift or a measure is written down.
Nothing here restates one, because two copies of `#0e6e5c` is one copy that goes stale.

| Piece | What it holds | Where |
| -- | -- | -- |
| The values | Every colour, radius, lift, height, face and measure | `web/app/assets/css/tokens.css` |
| The patterns | What a screen is, what a key is, what a page may do to what it draws | This file |

| What a session's answer must look like | The answer contract | `docs/answer-contract.md` |

**A session that changes one of these patterns changes this file in the same commit.** Each
section below names the file that enforces its rule, so a reader can check the claim rather
than trust it — and a rule whose enforcing file no longer says that is a rule that has been
quietly dropped.

## What was asked for, and what was not

A design pass of 15 October 2026 put four directions and seven problems to the developer who
uses this desk daily. His verdict, which is what the work between 15 and 16 October 2026 was
built to:

| Direction | Verdict |
| -- | -- |
| **Sharpen** — the editorial look, contained and tightened | **Yes.** App-wide. |
| **Workbench** — a dense list beside the thing it selects | **Yes, emphatically.** Code review and Draft. |
| **Triage** — a first pass that sorts before reading | No. |
| **Margin notes** — findings in the gutter of the diff | No. |

**"Sharpen" is app-wide and it is four concrete things**, each with its own section below:
the width is bounded and declared rather than drifting (*Two kinds of screen*), a list has
one title face and a one-line status cell (*A row is a row*), what is duplicated is folded
rather than dropped (*A page may fold or reorder…*), and a decision is a keystroke
(*A decision is one keystroke*). Sharpening is not a visual pass over everything; it is
these four rules applied wherever they bite.

And one thing that was not on the list. Understand, Alternatives and Solution map were
"quite broad, quite large, you've got to dig into them" — **a display problem, not a content
problem.** The content is good and he enjoys it. Nothing in this repository changes what a
session writes or how it is generated; the three steps became one page instead.

## The application shell (21 November 2026)

**Review Desk is a structured application, not a set of articles.** Patrick, 15 November 2026,
on the earlier direction: it still read *"very much like an article"*; take *"a completely fresh
look… just using best practice… really leaning into a much more structured application."* On
21 November, on the result: *"I honestly think it's perfect"* — the layout, structure and
workflow are settled; typography and styling may still move. The screens are in
`docs/mockups/s-structured`, and its README says which copy wins.

**Every screen sits in one shell of three columns:**

| Column | Default width | Limits | What it holds |
| -- | -- | -- | -- |
| Sidebar | 232px | 180–480px | The wordmark; **Pull requests** and **Rules**; pull requests grouped as being reviewed, waiting on the author, done this week; the GitHub and agent status lines |
| Main | the rest | never under 480px | The page: a review header and its tabs, or the list |
| Conversation | 380px | 300px to half the window, or 720px if that is smaller | **Ask this review**, on every review tab. Absent on the list and on Rules |
| Pull requests preview | 380px | the conversation's | The selected row, on the list (below) |

**The widths are defaults: each side column has a drag handle on its inner edge** (DEV-1375).
Patrick, 23 November 2026: *"there should be a handle there where I can move it. Likewise, on
the other side, too."* The handle is a focusable `role="separator"` with its value and limits;
the arrow keys move it 16px (64px with Shift), Home and End go to the limits, and a double-click
puts the default back. **The width set is kept per browser, across reloads**, in
`localStorage` read inside `try`, so blocked storage draws the defaults. **The main column always
keeps 480px**: when the window is too narrow for what was set, the right-hand column gives way
first, then the sidebar, and what was set comes back when there is room — a drag stops where
the main column would go under 480 rather than pushing the other column. Under 1,100px the
conversation has no handle; under 700px nothing does, and the phone's sidebar is 232px.
`web/app/utils/columns.ts` holds the limits and the arithmetic, `ColumnHandle.vue` the handle,
`web/test/columns.spec.ts` the rules, and `web/e2e/shell.spec.ts` drags each handle.

**How it is built** (DEV-1323). `web/app/layouts/default.vue` is the grid; `AppSidebar` is the
first column. Six rules it keeps, each in the file that holds it:

- **The groups are read off the record**, never worked out by the page: *Waiting on you* (which
  S1 and S2 draw first and open), *Being reviewed* and *Waiting on the author* from `GET /inbox`'s
  arrays, *Done this week* from the Reviews list's *Finished* view, one row per pull request.
  An empty group still draws, saying *None*. `sidebarGroups` in `web/app/utils/sidebar.ts`.
- **The state word is chosen once**, in `web/app/utils/stateWord.ts`. The sidebar's word is the
  inbox array a pull request is in. **A review the sidebar lists takes that row's word in its own
  header** (`stateOfReview(detail, rowFor(groups, …))`), because the inbox decides from more than
  one round — a reply on round 1 while round 3 waits — and one review's page cannot see the others.
  Any other round says what its own facts say, asked in `crates/store/src/entities/inbox.rs`'s
  order, with the pull request's end read off `not_for_signing` and a later round as
  *Superseded*. `web/test/state-word.spec.ts` bends the sample desk into the three shapes that
  once disagreed and asserts one word by both routes.
- **The GitHub line is drawn only when a read is recorded**: the newest `harvested_at` the two
  reads carry, and no line when there is none. `githubReadAt`.
- **The agent line is DEV-1140's reading**, which is per review, so it is drawn on a review's
  pages and nowhere else; absent is silent, as on the review's own strip. `agentLine`.
- **Two places in the navigation, Pull requests and Rules.** Reviews was a third until the
  one list landed (DEV-1325); `/reviews` redirects to that list's *Every review* view.
- **The conversation's column holds *Ask this review*** on a review's pages (DEV-1333): the
  layout draws the column and the review's page teleports `ConversationPanel` into it. Between
  700 and 1,100px it sits under the page, at the main column's width. Under 700px the shell is
  one column: the sidebar behind a menu button that closes on Escape, the sample-data marker
  in the bar, and the conversation a bottom sheet behind the bar's *Ask* (S14, DEV-1336, below).
  `web/e2e/shell.spec.ts` measures all of it at 2,560, 1,920, 1,600, 1,280, 1,024 and 390.

**Queue and Reviews are one list, Pull requests** (DEV-1325, S1 and S17), at `/`:

- **Its tabs are the sidebar's groups, under the sidebar's words** — *Waiting on you*, *Being
  reviewed*, *Waiting on the author* — then *Your own*, *Done* (the sidebar's *Done this week*)
  and **Every review**, which is the Reviews list drawn whole (`ReviewsList`): the dismissed,
  the finished before this week, the out of play and every earlier round are in no group, and
  the list must still reach every row the two pages drew. `test/screens.nuxt.spec.ts` asserts
  the tabs hold `sidebarGroups`'s rows. Every panel is drawn and the inactive ones hidden: the
  tabs fold the list, they do not remove any of it.
- **A status cell is the state word and one line of facts.** The word is `stateWord`'s; the
  session folds into the facts — its step, and what the record holds about it — rather than
  taking a column.
- **A row opens its review's Overview** (`tabPath`). `J` and `K` move the selection, `Enter`
  opens it, under `keyIsForThePage`.
- **The preview beside it draws the selected row from the record**: the bottom line from
  `bottomLine` in `web/app/utils/theCase.ts` — the brief's headline and `answerFacts`, and the
  one helper the Overview draws it with too — the state, the findings, what was not checked,
  the session, and `primaryAction`. A fact with no field is left out. It is not drawn under
  1,200px, where the table needs the width. The page asks for its column with
  `definePageMeta({ split: true })`.
- **When nothing waits on the developer** the table reads *Nothing needs you*, a line for each
  other group, and the preview *Since yesterday* — built from the three times the record keeps
  (posted, came back, finished) and nothing forecast. `sinceYesterday` in
  `web/app/utils/pullRequests.ts`.

**A review is one header and five tabs**, replacing the step trail:

| Tab | Was | What it answers |
| -- | -- | -- |
| Overview | the review page | Where it stands, the bottom line, the five questions you'd be asked |
| Understanding | Understand, Alternatives, Solution | The case, as one tab |
| Findings | Code review | The list and the one selected finding |
| Draft | Draft | What would post |
| Replies | What happened | What came back, and the three replies |

**Overview is three pages, chosen from the record** (DEV-1326; S2, S12, S15). Every rule is in
`web/app/utils/overview.ts` and is read through `stateOfReview`, so Overview cannot draw
*Since you posted* under a header saying *Draft ready*:

| Overview | When | Opens on | Then |
| -- | -- | -- | -- |
| Ready | brief or draft ready, posted, or off the desk | *The bottom line*: the brief's headline, and `answerFacts` as figures | *What you'd be asked*: five questions, each with its answer and the tab that holds it |
| Being written | a session is writing it, or none has picked it up | *Not written yet*, and the facts earned so far | The same questions, marked *Writing now* or *Not started*; findings with **no severity** |
| Replies in | the author or the harvester recorded something | *Since you posted*: fixed, answered, contested, no reply, new commits | *What came back*, a row per finding with its basis |

- **The outcome groups are one function**, `sinceYouPosted` in `web/app/utils/outcomes.ts`.
  *Contested* is `repliesToAnswer` by construction, so the Replies tab's count, the header's
  *Answer F3* and Overview cannot disagree. *Since round 1* (DEV-1329) and the Replies groups
  (DEV-1330) read it rather than grouping again.
- **Every outcome states its basis**: *ran*, *read*, *told* or *not re-checked*. The record holds
  no re-run, so nothing today says *ran*.
- **"New code under F6" only when the comparison says the finding's lines moved** —
  `lines_changed: true` on a `code_changed_after`. A file that changed around an unmoved line
  has no row.
- **Where it stands replaces the trail as the answer to *where is it***: Brief ready → Code
  review → Draft ready → Posted → Replies in. The seven-step trail is folded under the bottom line, because
  it still says what each step came to and how long it took, and nothing else does.

**The header's rules**, from the 15 November rules for every screen:

- **One state word**, the same word everywhere that review appears.
- **One next action, top right**, naming what it acts on (*Answer F3*, never *Continue*). A
  review with nothing for the developer to do has no primary action.
- **No taller than 120px.**
- **Times only when measured.** A time the record does not hold is left out, never estimated.
- **The session is visible wherever its review is**: the conversation header says who is
  answering (S11), and how.

**The conversation follows the answer contract** (`docs/answer-contract.md`): a headline, at most
five points each with its basis, cites, and at most three suggestions, each accepted or dismissed
by the developer. **Who answers is the developer's choice, and Review Desk never starts, resumes
or drives Claude on its own** (S11): with Allele the conversation is two way; with the
developer's own session it is one way, and the developer asks there; with neither it is read
only. Under 700px wide the conversation is a bottom sheet (S14).

## Ask this review is the conversation, drawn as the contract shapes it

**S6's panel beside every tab** (DEV-1333), drawing what `GET /reviews/{id}/messages` served
and never re-checking it. Each rule is in the file named:

- **Who is answering is one helper**, `answering` in `web/app/utils/answering.ts`, read off
  Allele's reading of the session and nothing else: a reading is two way, none is read only
  (*No agent connected · you can read, not ask*). Every question, the box's and *Ask it again,
  in the format*, leaves through the panel's one `send`, which asks `asksFromHere` first.
- **A reply is drawn in the shape the server parsed**: the headline, each point after its
  basis, the cites, *not sure*, the suggestions (which act, below); `working` as its activity steps; `cant`
  as *can't answer yet*; a reply that did not parse folded after ~200 characters with one
  button. A reply the server marks `superseded_by` is not drawn. `web/app/components/ConversationReply.vue`.
- **A cite is a link only when the record holds what it names**, and the session's words
  otherwise: `citeTarget` in `web/app/utils/cites.ts`. `F9` selects the finding through
  `findingPath`.
- **The questions an empty conversation starts with are offered only when the record holds
  their reason**, and *Asked so far* counts the developer's questions by the tab each was
  about. `suggestedQuestions` and `askedSoFar` in `web/app/utils/conversation.ts`.
- **Nothing in it is sized to the column**, so the phone's sheet hosts the same component.
- **On a phone it is a bottom sheet over the dimmed review** (DEV-1336, S14), opened by *Ask*
  in the bar on a review's pages. **The sheet is the column, not a copy of it**: under 700px
  `#conversation` is drawn fixed to the window's foot instead of not at all, so the panel
  the page teleported there is the one the sheet shows, with its thread and its ask box's
  text. The layout owns the container and nothing inside it — the grabber, the chevron that
  closes it, the scrim, `inert` on the page, and every `env(safe-area-inset-*)`. Escape,
  the scrim, going somewhere and widening past 700 close it, as they close the menu.
  `web/app/layouts/default.vue`; `web/e2e/phone-sheet.spec.ts` asks from it two way, and
  `web/e2e/shell.spec.ts` opens it on every tab at 390 and finds no sideways scroll.
- **A suggestion is accepted through the page's own control, and dismissed with one click**
  (DEV-1334, S8). Accept on `regrade`, `add_to_draft` and `set_aside` is the decision `G`, `E`
  and `S` make; on `new_finding`, and *Turn into a finding* on an answer, it is the one call
  that adds a finding, and Findings marks the finding *new*; a `draft_reply` fills the reply on
  Replies for the developer to send; a `follow_up` fills the ask box. An answered suggestion is
  drawn as one line in place of its buttons (*Added as F16 · should · ran*). The reason for a
  dismissal is asked after the click, never before it. **No Undo**: the page's decisions have
  none. `accepting` in `web/app/utils/suggestionActions.ts`; `SuggestionActions.vue`.

## Two kinds of screen

**A screen is a document or a workbench, and the difference is in what it draws, not how wide
it is.** Patrick, 23 November 2026 (DEV-1372):

> "It's not full screen… this is almost entirely never going to be used on a mobile device,
> it's always going to be used on desktop. Happy for it to be somewhat responsive… it needs to
> be fixed."

**Desktop is the target, and Review Desk uses the whole window.** The shell has no outer cap and
is not centred: the sidebar is against the window's left edge, the conversation against its
right on a review's pages, and the main column takes everything between them, on every page.
This replaces the two caps the section used to set — 1,600px around the shell
(`--rd-shell-wide`, 16 October 2026) and 1,240px around a document's main column
(`--rd-shell-max`) — and both tokens are gone from `tokens.css`.

| Width | Shell | Main column |
| -- | -- | -- |
| ≥1,100 | Sidebar at the left edge, 232px by default; conversation at the right edge on a review's pages, 380px by default; each dragged within its limits (*The application shell*); no cap, no centring | Everything between them, on every page, and never under 480px: at the defaults, 1,308px at 1,920 on a review, 2,328px at 2,560 on Rules |
| 700–1,099 | The conversation sits under the page | Full width |
| <700 | One column, the sidebar behind the menu, the conversation a bottom sheet (DEV-1336) | Full width |

| Screen | Kind | What fills the width |
| -- | -- | -- |
| Rules, one review, the case, What happened | Document | The bands — cards, tables, grids and rules. The paragraphs in them stop at their measure, left-aligned in the band |
| Pull requests | List beside its preview | The rows take what the preview leaves (380px by default, dragged like the conversation; `split: true`), and the preview meets the window's edge |
| Code review, Draft | Workbench | The columns, divided in fractions by container queries on the page's own width |

`web/e2e/shell.spec.ts` measures every page against this at 2,560, 1,920, 1,600 and 1,280: the
sidebar at x = 0, the conversation's and the preview's right edges at the window's, the main
column's width, a workbench's two columns, and no paragraph on a document's page whose text
runs wider than its measure.

A document is read down. A workbench is worked across: a dense list on the left, the one
thing selected drawn in full on the right, and a key for every decision. The developer
currently accepts and posts every finding because *"there's too much going on"* — the point
of the bench is that **Ticket and Set aside become as easy as Post**.

### Full width, and prose that does not grow with it

**Every page has the whole main column**, so there is nothing for a page to ask for: the
`definePageMeta({ wide: true })` Code review and Draft used to set went with the caps it lifted
them out of. **The width is contained by the measure, not by the shell.** That was always the
half of the old rule that did the work, and it is the half that stays:

> **Prose is capped by its own rule, never by the grid track it sits in.**

`.rd-recorded` stops recorded text at `--rd-measure-recorded`, about 70 characters. The first
version of the code review bench instead sized the *fields column* at that measure so the
hunk could take the rest, which is backwards at the width where it matters: 70ch resolves to
about 700px, so at a 1,440px window the fields took 699 of the 948 going, the code was left
247, and the page scrolled sideways by 18px. The columns divide what there is in fractions;
the paragraphs cap themselves. Enforced by `.columns` in
`web/app/pages/reviews/[id]/findings.vue`.

**A paragraph in a band that fills carries its own cap.** With the main column uncapped, a
`<p>` that leaned on the old 1,240 for its line length runs the band's width instead, so it takes
`--rd-measure` itself: `DeskNotice` (a notice ran 1,638px on What happened at 2,560) and the
answer lines of Overview's *What you'd be asked* (1,074px). A row of a key and a title, or a line
of figures, is a `<p>` too, but its box filling the band is the band filling — what is held to
the measure is how far the words run. The review header keeps its own caps at every width: the
title at 940px, the lead line at 800px.

**Under the shell, a workbench measures its own column, not the window** (DEV-1328). At a
1,600px window the main column beside the conversation is 988px, so a rule keyed on the
viewport would put two columns into room for one. Findings' bench and its `.columns` are
container queries: the list and the finding sit side by side from 720px of their container (1,440 is 748; 1,280 stacks), and
the fields sit beside the hunk only from 760px of the finding's own pane — which, with the
conversation present, is never — so the hunk always has the pane's full width.
`web/e2e/findings.spec.ts` asserts no sideways scroll on every finding at 1,600, with 16px to
spare.

## A decision is one keystroke

**Every key is the first letter of the button it presses, and the buttons are named for the
three lists the page sorts findings into.** Patrick, 16 October 2026, on the keys the first
bench had: *he has no muscle memory for them.* A developer who can read the button can type
the key.

| Key | Button | Decision in the record |
| -- | -- | -- |
| `P` | Post | `keep` on a finding this round holds open, `raise_again` on one it has settled |
| `T` | Ticket | `to_ticket` |
| `S` | Set aside | `cut` |
| `G` | Regrade | `regrade`, then the severity |
| `E` | Edit wording | `rewrite` |
| `R` / `A` / `W` | Raise it again / Accept their reason / Withdraw | the three replies, on a carried and settled finding only, on a draft that still takes decisions. On Findings and on Replies, from one rule (`answersTheAuthor`); on Replies they are bound to one reply at a time |
| `J` / `K` | — | move down and up the list |
| `P` / `N` | Promote / Not a rule | on **Rules** only, on a proposed rule (S10). Added 21 November 2026; rules are not wired yet, so the keys arrive with them |

**A key is its button's first letter on the page it is pressed on.** `P` is Post on Findings and
Promote on Rules; the two pages never draw both buttons.

**One label over two decisions, chosen by the record's own rule.** The store refuses `keep`
when the round is not open, and `raise_again` is the decision that says a settled finding is
still there — so Post is the way back from a ticket or from set aside, and a developer is
never asked which of two words means *post it* depending on what they pressed a moment ago.
`web/app/components/FindingCall.vue` draws it;
`crates/store/src/entities/decision.rs` is the refusal.

**One rule about when a key is not a key**, in `web/app/utils/keys.ts`, shared by the bench
and by `DecisionTrack`: not while the target is a field or `contenteditable`, not with a
modifier held, not while an IME is composing. `G` is a letter in "regrade" and `J` is a
letter in most sentences, so a second copy of this rule is the kind that drifts quietly.

## The verb a reader sees is the word on the button they pressed

| The record | What a reader reads |
| -- | -- |
| `cut` | **Set aside** |
| `kept` | **Posted** |
| `rewritten` | **Edited** |

The decision is `cut` in the record and always will be — it is in the contract and in every
row already written. "Cut" on a button, and in the sentence recording what was done, named
something harsher than the decision is. `web/app/utils/format.ts` holds the map; it is the
only place these three words are chosen.

## A page may fold or reorder what it draws, and may never remove any of it

**The rule, and the ruling it comes from.** An early version of the Draft page took the
duplicated index out of the preview and said so in a line naming the tab that still had it.
Patrick, 16 October 2026: *"we shouldn't be signing off on something that isn't what we're
posting."* The index keeps posting, so the page he signs off on has to hold it.

So: fold it, reorder it, summarise it on a line — and never drop a row. Three pages are
built to this rule:

| Page | What is folded | What the fold's line says | What asserts nothing was lost |
| -- | -- | -- | -- |
| Draft | The open index's heading and its table | How many findings it lists | `test/draft.spec.ts`: *draws every part of the stored body* |
| Every review (was Reviews) | Every round of a pull request but the newest in the answer | How many, which, and what became of them | Every round's link is reachable, face row and fold together |
| The case | The two flows, and each band's reference material | The pieces behind it, named | The summary interpolates the list of them |

Three mechanics that go with it:

- **`.rd-fold` is the app's fold control**, in `tokens.css`. A `display: flex` summary draws
  no native marker, so a fold with no rule of its own is a line of accent text with nothing
  to say a click opens it. The triangle is drawn, not typed, so it needs no glyph from the
  body font and turns with the fold.
- **A fold's summary names the states behind it when any of them is load-bearing.** A
  dismissal carries the developer's own words and a supersession says where a round went;
  "4 earlier rounds" alone would make a reader open every one to find out whether any
  mattered. `earlierSummary` in `web/app/components/ReviewsList.vue`.
- **The Draft's fold is markdown, not a control of the app's** — the `<details>` GitHub
  itself renders, written into the body. A preview whose job is fidelity folds the way the
  thing it previews folds. `foldOpenIndex` in `web/app/utils/draft.ts`.

## A row is a row

Both lists — the Queue and Reviews, one list since DEV-1325 — are a column of rows, and a
reader scanning a column is reading shapes. Four rules, all from the design pass's problems 05 and 07.

**One title face.** The serif is the page's own voice — an h1, a headline, the figure on a
card — and never a row's. A row whose title is set in a different face from the row under it
reads as a different *kind* of thing, which is a difference that means nothing. There was a
`.rd-display-row` token, Newsreader at 21px, used on exactly one line: the queue's needs-you
title. It is gone with its one caller, and **a token is deleted when its last caller goes.**
Emphasis inside a list is size and weight. **Under the shell the serif goes further back: one
use only, the "Review Desk" wordmark.** Patrick, 21 November 2026: *"review desk should have some
kind of… flair… It's like the name of the application. So I'm happy to have it as an
exception."* Headings, figures and titles are the sans, on the S type scale (22 / 19 / 16 / 14 /
13 / 12 / 11, `--rd-type-*` in `tokens.css`). The face is `--rd-font-wordmark` and the wordmark is
its only caller; `.rd-display-figure` went with its last caller. The rule is written over the
display block in `tokens.css`; `web/test/screens.nuxt.spec.ts` asserts *no serif on a row* and
reads every stylesheet for a second use of the face, and `web/e2e/shell.spec.ts` asks the browser
for the face of every element on every page.

**A status cell is a state line and one line of facts.** On the Queue, problem 05's exact
string — "0 replies · 0 threads resolved · 0 findings with code changed since · as at 24
min ago · pull request open at the last harvest" — filled three lines to say *nothing new*.
It now reads "Nothing back · read 13 hours ago". Nothing was dropped to get there: the three
noughts became one phrase saying the same thing, and the pull request's state moved up to
the row's meta line, where its other facts about the pull request already were.

**A nought is folded only when every figure beside it was measured.** `authorResponseLabel`
gates its fold on all three figures being non-null. A null is never a nought: a row with two
measured noughts beside one unknown draws the two.

**One row per pull request, with earlier rounds folded.** Reviews drew 13 rows for 8 pull
requests, #9541 five times, while the Queue already folded rounds. It draws 8.

> **A folded row's title is the newest round that *records* one** — deliberately the
> opposite of the Queue's rule. A Queue row is one round and says so when that round records
> no title; a Reviews row is the pull request. `#9541` holds five rounds of which only the
> newest records none, so reading the face round alone drew "no title recorded" over four
> rounds all carrying the same real title.

Two mechanics, both learned the hard way:

- **A `<details>` inside a row's anchor is the `<a>`-inside-`<a>` trap in another tag.** The
  fold is a *sibling* of the row's anchor, through `QueueRow`'s `#rounds` slot — otherwise
  pressing the summary follows the row's link. Asserted in a browser
  (`web/e2e/queue-rounds.spec.ts`), because it is the one thing a fake DOM cannot answer.
- **A nested row uses the parent's grid tracks, at the parent's widths.** The first version
  of the fold had its own grid and a 76px indent, and its sentences were a different width
  from the face row's directly above them.

## The case for a change is five bands on one tab and a derived answer line

Understand, Alternatives and Solution map were a page each — on review #9639, 3,653 + 3,132
+ 2,768 pixels and three navigations for one review. They are one page: a band per question,
**each band the shape of its own answer rather than a summary of it.**

It opens with the brief's own headline and then one line of facts: "4 problems · option B
built · fixes 3 of 4 · blind pass would pick D". The condition on that line, in his words:

> It is **derived from existing review data**. No new session-written summary, no new field,
> and **a fact that cannot be derived is left out of the line** rather than guessed at.

That condition is the whole design of `answerFacts` in `web/app/utils/theCase.ts`: each fact
is a separate test of the record, so a brief half way through being written draws the facts
it has earned and no others — the problem half alone draws "4 problems" and stops.

**Three steps are one page: the class says the look, `aria-current` says the address.** The
trail still draws three steps and they still reach three places, through `BAND_OF_STEP`.

**Under S3 it is the Understanding tab, five bands with *On this tab* down the left**
(DEV-1327): *What changes* (Today and After this PR over the numbered problems), *Ticket
against what was built* (the review's `criteria`), *Approach*, *What was built*, and *Not
verified* (the review's `not_checked`). Each band is headed by its question with its figures
beside it, outside the heading. `CASE_BANDS` in `web/app/utils/theCase.ts` is the one list of
them, and **its ids outlive its words**: `what-was-chosen` and `what-was-built` are where the
old Alternatives and Solution addresses land, and Overview links to `what-was-chosen` and
`not-verified`. S3's *Taken as true*, and the *Claimed* and *How* columns of its criteria
table, are not drawn: the record holds no assumptions and a criterion carries only what was
observed. *What was built* is not on S3 and stays, because nothing is removed. The rail is
drawn when the case's own container is 820px wide or more, not by the window.

## Findings is the list beside the one selected finding

**S4, the Findings tab** (DEV-1328), is the code review bench inside the shell. The list is
grouped by its three tabs, *To post*, *For a ticket* and *Set aside*, with *All parts* beside
them. All parts is the old strip of part tiles folded into one control, with every tile still
there as an option and its tally. Each row has the grade, the number, the title over where it is,
and how it was checked. The finding beside the list has its grade, number and basis, its
title, then *Where*, *Part* and *Raised before*. Under those are the fields, *How it was
checked* over the code, and the folded reasoning. The call and its keys are the pane's foot,
pinned to the window when the bench has two columns. In the document the call still comes
first, so on a phone or to a screen reader it is reached before the proof, as it was.

- **A basis is drawn only when the record holds one.** `verification` gives *Ran* or *Read*;
  `unknown` draws nothing. S4's *Told by author* and *Second reader* are not drawn: no record
  holds either. `basisOf` in `web/app/utils/findings.ts`.
- **One finding has one address: `?finding=F9`**, `findingPath` in
  `web/app/utils/reviewTabs.ts`. The header's *Answer F3*, Overview's *Needs your eye*, the
  case's finding lines and Replies all link with it. `#F9` still works, and so does
  `…/code-review#F9` through its redirect. `findingAsked` reads both forms.
- **The tab's count is the *To post* list**, as S4 counts it, read off `listCounts`. The
  page's three tabs count with the same function, so the tab and the list cannot disagree.

## Draft is what posts beside what you decide

**S05, the Draft tab** (DEV-1329), is the draft inside the shell: *What GitHub will show* with
its views (Rendered, Markdown, *Changes since…*, and the editor S05 does not draw), the
comments on the code as S05's table under it, and a side column of *Post as*, *Checks*,
*Held back*, your edits, the outline and the foot. The two sit side by side from 760px of the
tab's own width, a container query as Findings' bench is.

- **The sign-off is the header's primary action, and the page draws no second one.** The
  binding and every gate it had moved there: the page hands the header `ActOnTab`, offered
  only for a draft that is ready and can post, disabled while the draft is unread, edited
  and unsaved, or a write is in flight. Its label and the note under it come from
  `primaryAction` in `web/app/utils/reviewTabs.ts`. A later round reads *Sign off round 2
  and post*, and the note names the commit the round read, because a sign-off is withdrawn
  when the head moves past it (DEV-962). A draft that is signed off, sent back or being
  rewritten has no sign-off, not a disabled one. **On Draft the header is pinned** from 1,024px
  up, so the act stays in reach for the whole scroll, as the old aside's pinned panel kept it;
  the outline and the foot ride under it in the side column.
- **Post as is three segments**, radios under one legend, carrying the same `event`.
- **Each comment on the code is folded under its row**, never dropped. The row says *line
  unchanged* when the line was counted at the head, and a carried finding says *carried
  from round N*. S16's *thread continues* is not drawn, because a later round posts its own
  comment: `carry_finding` does not carry `github_comment_id`. *Re-anchored* and *moved from
  :n* are not drawn either, because a carry copies the line and its commit and nothing
  re-measures them.
- **A later round's *Since round 1* is read off the carried findings' own `round_status`**,
  `sinceRound` in `web/app/utils/outcomes.ts`, not off `sinceYouPosted`. A round's outcomes
  are its own, and opening round 2 copies none of round 1's.

## If you are a session writing the content

Nothing in the design loop changed the contract or what a session writes. These are the
things the pages now assume, which are worth knowing before you write the text they draw:

- **Write paragraphs in recorded prose fields.** `.rd-recorded` keeps your blank lines
  (`pre-wrap`) and wraps your long ones. It is **interpolated, never `v-html`** — a record
  is a record, not markup — and the shape of that rule is also why it can be: no HTML is
  needed to get a paragraph break back.
- **The draft body *is* markdown**, rendered and sanitised (`MarkdownView`, DOMPurify with
  `open` allowed so a `<details>` you write stays open). It is the one place markup is read.
- **Keep writing the open-findings index.** It is folded on the preview, not removed, and it
  still posts. `INDEX_HEADING` in `web/app/utils/houseStyle.ts` is the heading the fold looks
  for, and only the contiguous table under it is folded — prose under the same heading, and
  the `### Resolved in this PR` table, are left alone.
- **A brief's problem label heads a column** of the Alternatives matrix, so three words or
  fewer: a longer one heads a column with a sentence. `columnName` in `CaseChosen.vue`.
- **A part's `one_line` is drawn on a row that does not wrap.** `summary` is the longer text
  behind the row, and a part with no `one_line` shows its summary cut with an ellipsis.
- **Don't write a summary for the answer line.** It is derived, by rule.
- **A finding's `title` heads its own section** in the draft body; each nit raised gets its
  own section, because a section is what a per-finding decision rewrites.
