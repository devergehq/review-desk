# Design

**The look is editorial and it is contained.** — Patrick, 15 October 2026, on the design
pass: the serif, the sans and the one green stay; what had to go is the sprawl. *"Everything
seems to be a bit sprawling across the page at the moment."*

This file is the **patterns**. The **values** are in
[`web/app/assets/css/tokens.css`](../web/app/assets/css/tokens.css), which is documented at
length and is the only place a colour, a radius, a lift or a measure is written down.
Nothing here restates one, because two copies of `#0e6e5c` is one copy that goes stale.

| Piece | What it holds | Where |
| -- | -- | -- |
| The values | Every colour, radius, lift, height, face and measure | `web/app/assets/css/tokens.css` |
| The patterns | What a screen is, what a key is, what a page may do to what it draws | This file |
| The boards the values came from | Approved 10 October 2026, hex for hex | `docs/mockups/uplift` |
| The first five boards, and where the app departs | The 8 October reference | `docs/mockups/README.md` |
| The pictures | Every screen at a laptop and a phone, regenerated by a test | `docs/screenshots` |
| The before and after of each step | What each change actually looked like | Pull requests #64 to #70, and the loop record each one links |

**A session that changes one of these patterns changes this file in the same commit.** Each
section below names the file that enforces its rule, so a reader can check the claim rather
than trust it — and a rule whose enforcing file no longer says that is a rule that has been
quietly dropped.

## What was asked for, and what was not

A design pass of 15 October 2026 put four directions and seven problems to the developer who
uses this desk daily. His verdict, which is what the work between 15 and 16 October 2026 was
built to:

| Direction | Verdict |
| -- | -- |
| **Sharpen** — the editorial look, contained and tightened | **Yes.** App-wide. |
| **Workbench** — a dense list beside the thing it selects | **Yes, emphatically.** Code review and Draft. |
| **Triage** — a first pass that sorts before reading | No. |
| **Margin notes** — findings in the gutter of the diff | No. |

**"Sharpen" is app-wide and it is four concrete things**, each with its own section below:
the width is bounded and declared rather than drifting (*Two kinds of screen*), a list has
one title face and a one-line status cell (*A row is a row*), what is duplicated is folded
rather than dropped (*A page may fold or reorder…*), and a decision is a keystroke
(*A decision is one keystroke*). Sharpening is not a visual pass over everything; it is
these four rules applied wherever they bite.

And one thing that was not on the list. Understand, Alternatives and Solution map were
"quite broad, quite large, you've got to dig into them" — **a display problem, not a content
problem.** The content is good and he enjoys it. Nothing in this repository changes what a
session writes or how it is generated; the three steps became one page instead.

## Two kinds of screen

**A screen is a document or a workbench, and the difference decides its width.**

| Screen | Kind | Width |
| -- | -- | -- |
| Queue, Reviews, Rules, one review, the case, What happened | Document | `--rd-shell-max`, 1,240px |
| Code review, Draft | Workbench | `--rd-shell-wide`, 1,600px |

A document is read down. A workbench is worked across: a dense list on the left, the one
thing selected drawn in full on the right, and a key for every decision. The developer
currently accepts and posts every finding because *"there's too much going on"* — the point
of the bench is that **Ticket and Set aside become as easy as Post**.

### Full width, and prose that does not grow with it

A page asks for the wider shell itself, with `definePageMeta({ wide: true })`; the layout
reads `route.meta.wide` (`web/app/layouts/default.vue`). **Asked for by the page rather than
set into a store, so a page that is wide is wide from its first frame** and nothing resizes
under the reader.

The cap is what keeps "full width" contained. The second half of that is the measure:

> **Prose is capped by its own rule, never by the grid track it sits in.**

`.rd-recorded` stops recorded text at `--rd-measure-recorded`, about 70 characters. The first
version of the code review bench instead sized the *fields column* at that measure so the
hunk could take the rest, which is backwards at the width where it matters: 70ch resolves to
about 700px, so at a 1,440px window the fields took 699 of the 948 going, the code was left
247, and the page scrolled sideways by 18px. The columns divide what there is in fractions;
the paragraphs cap themselves. Enforced by `.columns` in
`web/app/pages/reviews/[id]/code-review.vue`.

## A decision is one keystroke

**Every key is the first letter of the button it presses, and the buttons are named for the
three lists the page sorts findings into.** Patrick, 16 October 2026, on the keys the first
bench had: *he has no muscle memory for them.* A developer who can read the button can type
the key.

| Key | Button | Decision in the record |
| -- | -- | -- |
| `P` | Post | `keep` on a finding this round holds open, `raise_again` on one it has settled |
| `T` | Ticket | `to_ticket` |
| `S` | Set aside | `cut` |
| `G` | Regrade | `regrade`, then the severity |
| `E` | Edit wording | `rewrite` |
| `R` / `A` / `W` | Raise it again / Accept their reason / Withdraw | the three replies, on a carried and settled finding only |
| `J` / `K` | — | move down and up the list |

**One label over two decisions, chosen by the record's own rule.** The store refuses `keep`
when the round is not open, and `raise_again` is the decision that says a settled finding is
still there — so Post is the way back from a ticket or from set aside, and a developer is
never asked which of two words means *post it* depending on what they pressed a moment ago.
`web/app/components/FindingCall.vue` draws it;
`crates/store/src/entities/decision.rs` is the refusal.

**One rule about when a key is not a key**, in `web/app/utils/keys.ts`, shared by the bench
and by `DecisionTrack`: not while the target is a field or `contenteditable`, not with a
modifier held, not while an IME is composing. `G` is a letter in "regrade" and `J` is a
letter in most sentences, so a second copy of this rule is the kind that drifts quietly.

## The verb a reader sees is the word on the button they pressed

| The record | What a reader reads |
| -- | -- |
| `cut` | **Set aside** |
| `kept` | **Posted** |
| `rewritten` | **Edited** |

The decision is `cut` in the record and always will be — it is in the contract and in every
row already written. "Cut" on a button, and in the sentence recording what was done, named
something harsher than the decision is. `web/app/utils/format.ts` holds the map; it is the
only place these three words are chosen.

## A page may fold or reorder what it draws, and may never remove any of it

**The rule, and the ruling it comes from.** An early version of the Draft page took the
duplicated index out of the preview and said so in a line naming the tab that still had it.
Patrick, 16 October 2026: *"we shouldn't be signing off on something that isn't what we're
posting."* The index keeps posting, so the page he signs off on has to hold it.

So: fold it, reorder it, summarise it on a line — and never drop a row. Three pages are
built to this rule:

| Page | What is folded | What the fold's line says | What asserts nothing was lost |
| -- | -- | -- | -- |
| Draft | The open index's heading and its table | How many findings it lists | `test/draft.spec.ts`: *draws every part of the stored body* |
| Reviews | Every round of a pull request but the newest in the answer | How many, which, and what became of them | Every round's link is reachable, face row and fold together |
| The case | The two flows, and each band's reference material | The pieces behind it, named | The summary interpolates the list of them |

Three mechanics that go with it:

- **`.rd-fold` is the app's fold control**, in `tokens.css`. A `display: flex` summary draws
  no native marker, so a fold with no rule of its own is a line of accent text with nothing
  to say a click opens it. The triangle is drawn, not typed, so it needs no glyph from the
  body font and turns with the fold.
- **A fold's summary names the states behind it when any of them is load-bearing.** A
  dismissal carries the developer's own words and a supersession says where a round went;
  "4 earlier rounds" alone would make a reader open every one to find out whether any
  mattered. `earlierSummary` in `web/app/pages/reviews/index.vue`.
- **The Draft's fold is markdown, not a control of the app's** — the `<details>` GitHub
  itself renders, written into the body. A preview whose job is fidelity folds the way the
  thing it previews folds. `foldOpenIndex` in `web/app/utils/draft.ts`.

## A row is a row

Both lists — the Queue and Reviews — are a column of rows, and a reader scanning a column
is reading shapes. Four rules, all from the design pass's problems 05 and 07.

**One title face.** The serif is the page's own voice — an h1, a headline, the figure on a
card — and never a row's. A row whose title is set in a different face from the row under it
reads as a different *kind* of thing, which is a difference that means nothing. There was a
`.rd-display-row` token, Newsreader at 21px, used on exactly one line: the queue's needs-you
title. It is gone with its one caller, and **a token is deleted when its last caller goes.**
Emphasis inside a list is size and weight. The rule is written over the display block in
`tokens.css`, and `web/test/screens.nuxt.spec.ts` asserts *no serif on a row*.

**A status cell is a state line and one line of facts.** On the Queue, problem 05's exact
string — "0 replies · 0 threads resolved · 0 findings with code changed since · as at 24
min ago · pull request open at the last harvest" — filled three lines to say *nothing new*.
It now reads "Nothing back · read 13 hours ago". Nothing was dropped to get there: the three
noughts became one phrase saying the same thing, and the pull request's state moved up to
the row's meta line, where its other facts about the pull request already were.

**A nought is folded only when every figure beside it was measured.** `authorResponseLabel`
gates its fold on all three figures being non-null. A null is never a nought: a row with two
measured noughts beside one unknown draws the two.

**One row per pull request, with earlier rounds folded.** Reviews drew 13 rows for 8 pull
requests, #9541 five times, while the Queue already folded rounds. It draws 8.

> **A folded row's title is the newest round that *records* one** — deliberately the
> opposite of the Queue's rule. A Queue row is one round and says so when that round records
> no title; a Reviews row is the pull request. `#9541` holds five rounds of which only the
> newest records none, so reading the face round alone drew "no title recorded" over four
> rounds all carrying the same real title.

Two mechanics, both learned the hard way:

- **A `<details>` inside a row's anchor is the `<a>`-inside-`<a>` trap in another tag.** The
  fold is a *sibling* of the row's anchor, through `QueueRow`'s `#rounds` slot — otherwise
  pressing the summary follows the row's link. Asserted in a browser
  (`web/e2e/queue-rounds.spec.ts`), because it is the one thing a fake DOM cannot answer.
- **A nested row uses the parent's grid tracks, at the parent's widths.** The first version
  of the fold had its own grid and a 76px indent, and its sentences were a different width
  from the face row's directly above them.

## The case for a change is three bands and a derived answer line

Understand, Alternatives and Solution map were a page each — on review #9639, 3,653 + 3,132
+ 2,768 pixels and three navigations for one review. They are one page: a band per question,
**each band the shape of its own answer rather than a summary of it.**

It opens with the brief's own headline and then one line of facts: "4 problems · option B
built · fixes 3 of 4 · blind pass would pick D". The condition on that line, in his words:

> It is **derived from existing review data**. No new session-written summary, no new field,
> and **a fact that cannot be derived is left out of the line** rather than guessed at.

That condition is the whole design of `answerFacts` in `web/app/utils/theCase.ts`: each fact
is a separate test of the record, so a brief half way through being written draws the facts
it has earned and no others — the problem half alone draws "4 problems" and stops.

**Three steps are one page: the class says the look, `aria-current` says the address.** The
trail still draws three steps and they still reach three places, through `BAND_OF_STEP`.

## If you are a session writing the content

Nothing in the design loop changed the contract or what a session writes. These are the
things the pages now assume, which are worth knowing before you write the text they draw:

- **Write paragraphs in recorded prose fields.** `.rd-recorded` keeps your blank lines
  (`pre-wrap`) and wraps your long ones. It is **interpolated, never `v-html`** — a record
  is a record, not markup — and the shape of that rule is also why it can be: no HTML is
  needed to get a paragraph break back.
- **The draft body *is* markdown**, rendered and sanitised (`MarkdownView`, DOMPurify with
  `open` allowed so a `<details>` you write stays open). It is the one place markup is read.
- **Keep writing the open-findings index.** It is folded on the preview, not removed, and it
  still posts. `INDEX_HEADING` in `web/app/utils/houseStyle.ts` is the heading the fold looks
  for, and only the contiguous table under it is folded — prose under the same heading, and
  the `### Resolved in this PR` table, are left alone.
- **A brief's problem label heads a column** of the Alternatives matrix, so three words or
  fewer: a longer one heads a column with a sentence. `columnName` in `CaseChosen.vue`.
- **A part's `one_line` is drawn on a row that does not wrap.** `summary` is the longer text
  behind the row, and a part with no `one_line` shows its summary cut with an ellipsis.
- **Don't write a summary for the answer line.** It is derived, by rule.
- **A finding's `title` heads its own section** in the draft body; each nit raised gets its
  own section, because a section is what a per-finding decision rewrites.
